Yes — below is a concrete, browser-friendly TypeScript structure you can start building immediately. Matter.js is a good fit because it provides rigid bodies, collisions, friction, gravity, events, and stable stacking, which are exactly the pieces a coin pusher MVP needs. ## Folder roles

A good rule is: `data/` holds static content, `models/` holds type contracts, `systems/` contains gameplay rules, and `physics/` owns Matter.js integration.  That separation matters because the coin pusher feel comes from both simulation and game economy, and you want to tweak each side without breaking the other. [youtube](https://www.youtube.com/watch?v=Bt4R2M_gS3Q)

- `core/`: bootstrapping, frame loop, config, event bus.
- `physics/`: Matter engine, board geometry, shelf motion, sensors, collision labels. [youtube](https://www.youtube.com/watch?v=Bt4R2M_gS3Q)
- `render/`: custom canvas drawing and juice effects rather than relying on default Matter rendering. [youtube](https://www.youtube.com/watch?v=Bt4R2M_gS3Q)
- `data/`: balancing content you can edit quickly during tuning.
- `models/`: TypeScript types/interfaces for compile-time safety.
- `systems/`: the heart of gameplay.
- `state/`: serializable runtime state for the current run.
- `ui/`: HTML overlay logic for HUD, shop, summary panels. [playraccoin](https://www.playraccoin.com)

## Core data models

The first-pass model should stay data-driven, because RACCOIN’s appeal comes from combining coin definitions and item modifiers into synergies.  In practice, that means your code should ask “what tags and effects does this coin have?” instead of hardcoding special behavior all over the place. [dev](https://dev.to/davidmorais/building-a-roguelike-game-with-typescript-105l)

## Runtime state shape

Your state should be plain and serializable, even if you also keep Matter bodies in maps outside the state. Matter body references are not the source of truth; your run state is.  This keeps game rules testable and prevents physics objects from leaking into UI and shop logic. [brm](https://brm.io/matter-js/)

## System responsibilities

Keep each system boring and narrow. The easiest way to lose control of a simulation game is to let payout logic, combo logic, and physics callbacks all mutate everything directly. [brm](https://brm.io/matter-js/)

- `drop-system.ts`: picks the next coin, spawns it, decrements drops.
- `machine-system.ts`: moves the pusher shelf on a timed cycle.
- `payout-system.ts`: detects front sensor exits and awards gold/score.
- `combo-system.ts`: calculates chains based on payout timing.
- `effect-system.ts`: resolves coin and item effects by trigger.
- `round-system.ts`: checks win/loss conditions and advances phases.
- `shop-system.ts`: rolls offers from weighted item/coin tables.

A useful pattern is: physics event -> dispatch gameplay event -> systems consume it -> state updates -> UI refresh. Matter.js already exposes events, so this pattern fits the engine naturally. [youtube](https://www.youtube.com/watch?v=Bt4R2M_gS3Q)

## Suggested starter interfaces for systems

### `src/core/event-bus.ts`

```ts
export type GameEvent =
  | { type: 'coin.spawned'; coinId: string; coinTypeId: string }
  | { type: 'coin.landed'; coinId: string }
  | { type: 'coin.payout'; coinId: string; lane: 'left' | 'center' | 'right' }
  | { type: 'coin.fuseExpired'; coinId: string }
  | { type: 'round.started'; roundNumber: number }
  | { type: 'round.ended'; roundNumber: number; cleared: boolean }
  | { type: 'shop.entered'; roundNumber: number };

type Handler<T extends GameEvent = GameEvent> = (event: T) => void;

export class EventBus {
  private handlers: Handler[] = [];

  emit(event: GameEvent) {
    for (const handler of this.handlers) handler(event);
  }

  on(handler: Handler) {
    this.handlers.push(handler);
    return () => {
      this.handlers = this.handlers.filter((h) => h !== handler);
    };
  }
}
```

## Recommended first implementation order

Build the codebase in the same order the player experiences the game. Matter.js supports stacking, collisions, friction, momentum, and events, so start by proving the machine feel before adding meta layers. [brm](https://brm.io/matter-js/)

1. `physics/world.ts` + `physics/board.ts`
2. `drop-system.ts`
3. `payout-system.ts`
4. `round-system.ts`
5. `data/coin-defs.ts` with `normal`, `heavy`, `bomb`
6. `item-defs.ts`
7. `effect-system.ts`
8. `shop-system.ts`
9. particles, shake, sound polish

## Practical advice

For MVP v1, do not model everything as classes. A data-first approach with plain interfaces plus small systems will let you rebalance faster and add new coins cleanly.  Also keep Matter bodies in a `Map<CoinId, Body>` inside `physics/world.ts`, while `RunState.activeCoins` holds only serializable gameplay data; that split will save you a lot of debugging later. [dev](https://dev.to/davidmorais/building-a-roguelike-game-with-typescript-105l)
